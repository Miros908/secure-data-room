# Data Room

Приложение для обмена файлами. Файлы лежат во вложенных папках; ими можно поделиться публичной ссылкой или с конкретным человеком, поставить срок доступа и отозвать его. Владелец видит, кто открывал и скачивал файлы.

## Деплой

- Фронтенд (Vercel): https://deal-box.vercel.app
- Backend API (Render): https://secure-data-room.onrender.com
- PostgreSQL тоже задеплоен на Render, рядом с API. Публичного URL у базы нет.

## Возможности

- [x] Регистрация и вход по email и паролю
- [x] Изоляция комнат данных разных пользователей
- [x] Вложенные папки, хлебные крошки, переименование и удаление
- [x] Загрузка нескольких файлов с прогрессом, просмотр в интерфейсе
- [x] Переименование, перемещение и удаление файлов
- [x] Версии: повторный upload того же имени в ту же папку не создаёт дубликат
- [x] Публичная ссылка и доступ конкретному пользователю, в том числе со сроком
- [x] Отзыв доступа
- [x] Живое обновление открытых вкладок при отзыве, истечении доступа и удалении
- [x] Журнал владельца: просмотры, скачивания, открытия ссылки, выдача и отзыв, удаления
- [x] Поиск по имени файла и папки по всей Data Room (на backend, с тем же ACL, что и listing)

## Стек

Монорепозиторий pnpm: Next.js 16 и React 19 на фронте, NestJS 11 API, PostgreSQL 16 и Prisma 7, файлы на диске или в Cloudflare R2. Прод: UI на Vercel; API и PostgreSQL на Render.

Библиотеки и версии — [стек](./stack.md).

## Использование AI

AI использовался в проекте как инструмент для ускорения разработки, а не как замена инженерного проектирования и принятия решений. Архитектура приложения, модель данных, границы модулей, правила авторизации, требования к целостности данных и основные технические решения проектировались и проверялись мной вручную.

Основной рабочий процесс выглядел следующим образом: сначала формировался конкретный план реализации задачи с ожидаемым поведением, ограничениями и затрагиваемыми частями системы. После ручной проверки и корректировки плана реализация отдельных, преимущественно рутинных задач делегировалась Cursor с использованием Composer 2.5. Полученный код после этого проходил ручную проверку на соответствие архитектуре, бизнес-логике проекта и ожидаемым edge cases.

Более сильная модель Opus 5 использовалась отдельно как дополнительный уровень ревью: для рефакторинга, поиска потенциальных дефектов, анализа сложных участков кода, проверки нарушений архитектурных границ, дублирования и возможных проблем безопасности. Таким образом, AI применялся в нескольких ролях — как исполнитель заранее определённых задач и как дополнительный инструмент code review, — при этом финальная ответственность за архитектуру, корректность логики и принимаемые технические решения оставалась за мной.

## Не реализовано

- Поиск по тексту внутри файлов
- Один поиск сразу по всем расшаренным комнатам (входящие шары остаются отдельным списком)
- Поиск на сервере в журнале, входящих и исходящих шарах (там по-прежнему фильтр уже загруженной страницы)
- Фильтры поиска по дате, размеру или типу
- Перемещение папок
- Несколько Data Room у одного владельца
- Вход через Google, подтверждение почты, сброс пароля
- Пагинация listing папки
- Исключения ACL («всё в папке, кроме этого файла»)
- Фоновые воркеры, превью, экспорт
- Redis, чтобы SSE доходил до каждой replica API
- Сбор сирот в object storage
- Политика хранения старых версий файлов и журнала
