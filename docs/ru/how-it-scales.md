# How it scales

Текущая модель рассчитана на рост без необходимости менять базовые сущности: файлы и папки принадлежат Data Room, доступ выдаётся на уровне комнаты, папки или файла, а версии файлов хранятся отдельно от основной записи файла.

## Data Room с 100 000 файлов

API не загружает дерево Data Room целиком. При открытии папки запрашиваются только её непосредственные дочерние папки и файлы:

* `GET /folders?dataRoomId=...`
* `GET /folders/:id`

В listing возвращаются метаданные файлов, а не содержимое PDF. Сам файл загружается отдельно по signed URL только при открытии.

Поэтому количество файлов во всём Data Room само по себе не увеличивает размер ответа при открытии конкретной папки. Стоимость listing зависит в первую очередь от количества элементов внутри открытой папки.

Для этих запросов используются индексы:

```text
folders: (data_room_id, parent_id, name, id)
files:   (data_room_id, folder_id, name, id)
```

Текущее ограничение — пагинации в listing пока нет. Если одна папка начнёт содержать тысячи файлов или подпапок, следующий шаг — перенести пагинацию на backend и использовать keyset pagination по `(name, id)`:

```sql
WHERE (name, id) > (...)
ORDER BY name, id
LIMIT n
```

Offset pagination для больших каталогов использоваться не должна, поскольку её стоимость растёт вместе с глубиной страницы.

Сортировка по другим полям, например дате или размеру, также должна выполняться на сервере вместе с соответствующими индексами.

Поиск — `GET /search`, не folder listing. ACL в том же SQL, что и совпадение имени ([архитектура](./architecture.md)). Маски в `q` экранируются. Результаты — keyset по `(name, kind, id)` с `LIMIT` (по умолчанию 20, максимум 50). Подстрока `ILIKE` использует GIN trigram-индексы:

```text
files_name_trgm_idx
folders_name_trgm_idx
```

плюс существующий btree по `data_room_id`. `COUNT(*)` и `OFFSET` нет.

## Размер и количество элементов в папке

Для операций над поддеревом используется `countSubtree`.

Перед удалением папки определяется:

* количество вложенных папок;
* количество файлов внутри всего поддерева.

Descendant-папки определяются по `path`, после чего учитываются файлы, принадлежащие этим папкам.

Сейчас этот механизм используется для предупреждения пользователя перед удалением и не выполняется при каждом открытии папки.

Размер всего поддерева в байтах сейчас отдельно не рассчитывается. Если он понадобится, к тому же subtree-запросу можно добавить агрегирование `SUM(size_bytes)` по найденным файлам.

Постоянные счётчики на `folders` сейчас не хранятся, поэтому нет дополнительной логики их синхронизации при upload, delete или move.

## Sharing и роли

Доступ хранится отдельно от дерева файлов: грант на комнату, папку или файл. `VIEWER` / `EDITOR` уже в модели, отдельная таблица ролей не нужна. Наследование и `already_covered` — [архитектура](./architecture.md).

Грант на папку не создаёт строку на каждый вложенный файл: расшаренная папка на 100 000 файлов — всё ещё одна строка гранта.

Владелец — `data_rooms.owner_id`, не `access_grant`. Отзыв гранта не удаляет ownership.

## Несколько Data Room у одного пользователя

Сейчас `owner_id` уникален, поэтому один пользователь владеет одной Data Room, которая создаётся при регистрации.

При этом остальные сущности уже привязаны к `data_room_id`:

* folders;
* files;
* access grants;
* public links;
* audit log;
* file versions.

Поэтому для поддержки нескольких Data Room у одного владельца потребуется убрать unique-ограничение с `owner_id` и добавить выбор комнаты в UI.

Структуру файлов и механизм sharing при этом менять не потребуется.

## Версии файлов

Повторная загрузка файла с тем же именем не создаёт дополнительную строку в folder listing.

Основная запись остаётся в `files`, а версии хранятся отдельно в `file_versions`.

Текущая версия определяется через:

```text
current_version_id
```

Поэтому увеличение количества версий не увеличивает количество файлов, возвращаемых при listing папки.

Конкретную версию можно открыть через:

```text
GET /files/:id/versions/:versionId
```

При большом количестве версий основным растущим ресурсом становятся таблица версий и blob storage. Политика удаления старых версий сейчас не реализована.

## Audit log

Audit log append-only.

История не загружается целиком: события выдаются страницами по cursor pagination:

```text
(created_at, id)
```

Размер страницы — 20 событий.

Используется индекс:

```text
(data_room_id, created_at, id)
```

Поэтому увеличение общей истории комнаты не требует загрузки всех предыдущих событий.

TTL или архивирование старых событий сейчас не реализованы.

## Несколько экземпляров API

Сессии хранятся в PostgreSQL, поэтому авторизация не зависит от памяти конкретного NestJS-процесса.

Несколько API-инстансов могут обрабатывать запросы без sticky sessions.

При этом live-события сейчас находятся в памяти процесса. Если запустить несколько экземпляров API, событие, созданное на одном экземпляре, не будет автоматически доставлено клиенту, подключённому к другому.

Это ограничение касается live-уведомлений, а не самой проверки доступа: `ResolveService` остаётся источником решения об авторизации при REST-запросе.

Для синхронизации live-событий между несколькими API-инстансами потребуется внешний pub/sub, например Redis. Сейчас такой механизм не реализован.
