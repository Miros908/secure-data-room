# How it scales

Поточна модель розрахована на ріст без потреби змінювати базові сутності: файли й папки належать Data Room, доступ видається на рівні кімнати, папки або файла, а версії файлів зберігаються окремо від основного запису файла.

## Data Room зі 100 000 файлів

API не завантажує дерево Data Room цілком. Під час відкриття папки запитуються лише її безпосередні дочірні папки й файли:

* `GET /folders?dataRoomId=...`
* `GET /folders/:id`

У listing повертаються метадані файлів, а не вміст PDF. Сам файл завантажується окремо за signed URL лише під час відкриття.

Тому кількість файлів у всьому Data Room сама по собі не збільшує розмір відповіді під час відкриття конкретної папки. Вартість listing залежить насамперед від кількості елементів усередині відкритої папки.

Для цих запитів використовуються індекси:

```text
folders: (data_room_id, parent_id, name, id)
files:   (data_room_id, folder_id, name, id)
```

Поточне обмеження — пагінації в listing поки немає. Якщо одна папка почне містити тисячі файлів або підпапок, наступний крок — перенести пагінацію на backend і використати keyset pagination за `(name, id)`:

```sql
WHERE (name, id) > (...)
ORDER BY name, id
LIMIT n
```

Offset pagination для великих каталогів використовуватися не повинна, оскільки її вартість росте разом із глибиною сторінки.

Сортування за іншими полями, наприклад датою або розміром, також має виконуватися на сервері разом із відповідними індексами.

Пошук — `GET /search`, не folder listing. ACL у тому самому SQL, що й збіг імені ([архітектура](./architecture.md)). Маски в `q` екрануються. Результати — keyset за `(name, kind, id)` з `LIMIT` (типово 20, максимум 50). Підрядок `ILIKE` використовує GIN trigram-індекси:

```text
files_name_trgm_idx
folders_name_trgm_idx
```

плюс наявний btree за `data_room_id`. `COUNT(*)` і `OFFSET` немає.

## Розмір і кількість елементів у папці

Для операцій над піддеревом використовується `countSubtree`.

Перед видаленням папки визначається:

* кількість вкладених папок;
* кількість файлів усередині всього піддерева.

Descendant-папки визначаються за `path`, після чого враховуються файли, що належать цим папкам.

Зараз цей механізм використовується для попередження користувача перед видаленням і не виконується під час кожного відкриття папки.

Розмір усього піддерева в байтах зараз окремо не розраховується. Якщо він знадобиться, до того самого subtree-запиту можна додати агрегування `SUM(size_bytes)` за знайденими файлами.

Постійні лічильники на `folders` зараз не зберігаються, тому немає додаткової логіки їхньої синхронізації при upload, delete або move.

## Sharing і ролі

Доступ зберігається окремо від дерева файлів: грант на кімнату, папку або файл. `VIEWER` / `EDITOR` уже в моделі, окрема таблиця ролей не потрібна. Наслідування і `already_covered` — [архітектура](./architecture.md).

Грант на папку не створює рядок на кожен вкладений файл: розшарена папка на 100 000 файлів — усе ще один рядок гранта.

Власник — `data_rooms.owner_id`, не `access_grant`. Відкликання гранту не видаляє ownership.

## Кілька Data Room в одного користувача

Зараз `owner_id` унікальний, тому один користувач володіє однією Data Room, яка створюється під час реєстрації.

При цьому решта сутностей уже прив’язані до `data_room_id`:

* folders;
* files;
* access grants;
* public links;
* audit log;
* file versions.

Тому для підтримки кількох Data Room в одного власника потрібно зняти unique-обмеження з `owner_id` і додати вибір кімнати в UI.

Структуру файлів і механізм sharing при цьому змінювати не доведеться.

## Версії файлів

Повторне завантаження файла з тим самим іменем не створює додатковий рядок у folder listing.

Основний запис лишається в `files`, а версії зберігаються окремо в `file_versions`.

Поточна версія визначається через:

```text
current_version_id
```

Тому збільшення кількості версій не збільшує кількість файлів, що повертаються під час listing папки.

Конкретну версію можна відкрити через:

```text
GET /files/:id/versions/:versionId
```

За великої кількості версій основним ресурсом, що росте, стають таблиця версій і blob storage. Політика видалення старих версій зараз не реалізована.

## Audit log

Audit log append-only.

Історія не завантажується цілком: події видаються сторінками за cursor pagination:

```text
(created_at, id)
```

Розмір сторінки — 20 подій.

Використовується індекс:

```text
(data_room_id, created_at, id)
```

Тому збільшення загальної історії кімнати не вимагає завантаження всіх попередніх подій.

TTL або архівування старих подій зараз не реалізовані.

## Кілька екземплярів API

Сесії зберігаються в PostgreSQL, тому авторизація не залежить від пам’яті конкретного NestJS-процесу.

Кілька API-інстансів можуть обробляти запити без sticky sessions.

При цьому live-події зараз перебувають у пам’яті процесу. Якщо запустити кілька екземплярів API, подію, створену на одному екземплярі, не буде автоматично доставлено клієнту, підключеному до іншого.

Це обмеження стосується live-сповіщень, а не самої перевірки доступу: `ResolveService` лишається джерелом рішення про авторизацію при REST-запиті.

Для синхронізації live-подій між кількома API-інстансами знадобиться зовнішній pub/sub, наприклад Redis. Зараз такий механізм не реалізований.
